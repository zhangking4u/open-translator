Running Translation Models Locally: What Actually Matters

Every translation product eventually has to decide where the model runs. The cloud route is easy to start and hard to leave, while local inference trades convenience for control. This article walks through the engineering considerations we hit while building a fully local translator.

The first argument for local processing is not privacy in the abstract. It is latency: a warm model on the same machine answers a short paragraph in a few hundred milliseconds, and no network hop can beat that.

Memory is the real budget

A quantized 1.8B model can fit comfortably in four gigabytes of RAM, but the context window is what usually blows the budget. Attention cost grows with sequence length, and every extra token of prompt is paid on every request.

We keep the default context window modest and make it configurable. Users who translate longer documents raise it deliberately, and everyone else keeps the fast path.

Quantization is the other lever. Four-bit weights cut the file size by roughly a factor of four with a small quality cost that is hard to notice in paragraph-level translation.

The fastest request is the one you never send: caching a paragraph that was already translated beats any optimization of the model itself.

The prompt is a contract

Instruction-tuned models are sensitive to prompt shape. A prompt that asks for a translation and a prompt that asks for a JSON object produce very different failure modes, and mixing the two in one string invites trouble.

We keep one style per model family. The HY-MT template is already source-agnostic, which means the detector never has to be perfect before the translator runs.

  • Keep the source language optional so auto-detection can stay best-effort.
  • Never inject user text into the instruction part of the prompt.
  • Preserve numbers, code fragments and product names whenever possible.
  • Return one line per input line when the caller sends a batch.

Streaming changes the experience

Streaming does not make the model faster. It changes when the user sees the first useful token, and that number dominates perceived quality for anything longer than a sentence.

Our server emits server-sent events with one delta per decoded piece and a terminal event that carries the elapsed time. The extension and the desktop card consume the same stream.

A streaming client also needs an idle timeout, not just a total one. A model that pauses between tokens should still be cancelled if the pause grows past a threshold.

Glossaries beat fine-tuning

Product names and UI terms are where generic translation falls apart. Fine tuning on a glossary is expensive and brittle; injecting the terms into every prompt is cheap and reversible.

The glossary file uses one source=target pair per line, capped at fifty entries. That cap is a prompt-budget decision, not a technical one.

Hardware is not the bottleneck

On a modern laptop the encoding phase of a short paragraph is dominated by prompt processing, and prompt processing is dominated by the context window. Once the prompt is cached, token generation is fast enough to feel interactive.

The practical limit is memory bandwidth. A model that fits entirely in cache behaves very differently from one that streams weights from system memory on every token.

Shipping the runtime is the hard part

Local inference means shipping a runtime, and shipping a runtime means dealing with platforms. Dynamic loading keeps the binary small but turns a load failure into a runtime error instead of a build error.

We pin one ONNX Runtime version for OCR and reuse the speech runtime for the rest. Two runtimes in one process is a recipe for very confusing crashes.

Version pinning is not glamorous. It is the difference between a release that reproduces on a user's machine and a support thread that never ends.

What we would do differently

We would measure end-to-end latency before choosing a model size. A smaller model with a tighter prompt beats a larger model with a sprawling one on almost every interactive workload.

We would also keep the translation cache persistent from day one. A session cache helps, but a disk cache survives the tab reloads that are the norm on the web.

Conclusion

Local translation is not a feature you add at the end of a product. It is an architectural decision that shapes prompts, packaging and the update story.

The good news is that the pieces compose: one text pipeline, one scheduling model, and a runtime that stays on the machine where the text already lives.
