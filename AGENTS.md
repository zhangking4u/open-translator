# AGENTS.md

OpenTranslator: local-first AI translation platform. Five Rust crates plus a browser extension exist: `core/translator-service` (HTTP service + engines), `core/inference` (llama.cpp actor engine), `desktop/translator-core` (platform-agnostic desktop lib), `desktop/translator-popup` (Linux/GNOME GTK popup), `desktop/translator-popup-desktop` (Windows/macOS eframe client) and `browser/extension`. `tests/` is an empty placeholder; `README.md` is the user guide — `docs/` is the project context.

## Repo layout / build

- The core crate is `core/translator-service`. There is no root Cargo.toml or workspace: run all cargo commands from the crate directory:
  - `cargo run` — Axum server at `TRANSLATOR_BIND_ADDR` (default `http://127.0.0.1:17890`)
  - `cargo test` — unit tests plus `tests/api.rs` (tower `oneshot`) and `tests/ollama.rs` (local axum stub server) integration tests; no external services needed
  - `cargo check`
- `core/inference` (crate `translator-inference`) wraps llama.cpp via `llama-cpp-2` using an actor worker thread (safe Rust, requests serialized over a channel): `InferenceEngine::load(model_path, LoadOptions)` + `generate(prompt, stop_strings, GenerateOptions)` + `generate_streaming(..., on_delta)` which reports every decoded token piece to a callback. Building it needs cmake + clang/libclang (see the dev-machine bullet); the real-model test is gated by `TRANSLATOR_TEST_MODEL`. It backs the service's `llama-cpp` engine and the embedded Windows/macOS desktop client (Phase B2/B3 done).
- `desktop/translator-core` is a platform-agnostic lib (no GTK): CLI args/config precedence, HTTP translate client (`translate::translate`, plus `translate::translate_stream` which parses the SSE deltas from `POST /translate/stream`), service health checks and auto-start, per-OS paths (Linux XDG, Windows `%APPDATA%`/`%LOCALAPPDATA%`, macOS `~/Library`), the shared language list (`languages::LANGUAGES` / `languages::label` / `languages::source_options` with the `auto` entry), source-language detection (`detect::detect` using `whatlang` trigrams, `detect::resolve_source` replaces `auto` with a detected tag when confident and keeps `auto` otherwise), the model downloader (`models::download`: ModelScope URL + SHA-256, resume via HTTP Range, `download_client()` sets a User-Agent because ModelScope's CDN returns 403 without one; `reqwest` needs the `rustls-tls` feature for it), and the startup update check (`update::check` against the GitHub `releases/latest` API, which also parses the release `assets` so the client can pick its update package; the release workflow embeds the tag via `OPEN_TRANSLATOR_VERSION`; `check_updates` / `TRANSLATOR_CHECK_UPDATES` toggles it). CI runs its tests on ubuntu, windows and macos. The Windows/macOS desktop clients are planned to build on this crate.
- `desktop/translator-popup` is the Linux/GNOME client and depends on `translator-core` by path: run cargo from `desktop/translator-popup/`. It calls the core service over HTTP, reads the Wayland selection via `wl-paste` (from the `wl-clipboard` package, installed on the dev machine; falls back to the clipboard when the primary selection is empty) and shows a GTK4 window (building it needs `libgtk-4-dev` + `pkg-config`); `--stdin` and `--print` keep it scriptable and testable. `~/.config/open-translator/config` (`service_url`/`source`/`target`/`clipboard`, plus `model_path`/`prompt_style`/`auto_download`/`check_updates`) is read with CLI > file > env precedence; the in-window source/target language dropdowns re-translate and write the choice back to that file (`source` defaults to `auto`; detection result shown next to the dropdown); a flat swap-icon button between the selectors exchanges the pair and feeds the previous translation back as the new source, and Ctrl+1/2/3 switch the recent targets (`recent_targets`); a header 剪贴板 toggle switches between the primary selection and the clipboard and persists it as `clipboard`. The window is a CSS-styled card layout driven by a translation state machine (spinner, download progress bar, error card + 重新翻译, 2 s copy feedback, Ctrl+Enter retranslate / Ctrl+Shift+C copy, dismissible update banner); the translation streams in from `POST /translate/stream` (`translate::translate_stream`) and renders piece by piece while a status line shows the received character count, and its height follows the translation up to 70% of the monitor and then scrolls. On startup it checks `/health` and auto-starts the core release binary if needed (detached, logs in `~/.local/state/open-translator/`); the default engine is in-process llama.cpp with first-run model download (`TRANSLATOR_ENGINE=ollama` keeps the legacy Ollama path, `TRANSLATOR_MODEL_PATH` points at an existing GGUF, `--no-start` disables auto-start). `desktop/install.sh` builds both crates in release and delegates shortcut registration to `packaging/linux/open-translator-setup` (`--uninstall` removes it); `packaging/linux/make-deb.sh` builds the deb (popup + service as siblings in `/usr/lib/open-translator`, desktop entry, icon; needs glibc ≥ 2.39 / GTK4 4.10 because it builds on Ubuntu 24.04) and the popup auto-registers the shortcut on first launch via `open-translator-setup --if-missing`. GNOME/Mutter does not implement the data-control protocol, so `wl-clipboard-rs` cannot be used.
- `desktop/translator-popup-desktop` is the Windows/macOS client (eframe/egui; the installers' login shortcut/LaunchAgent passes `--autostart`, which starts silently in the tray — first-run downloads and model errors also surface in the tray tooltip and in a system notification while the window is hidden (`src/notify.rs`: WinRT toast via `tauri-winrt-notification` on Windows, `mac-notification-sys` on macOS) — while a manual launch (no flag) shows the window; the window is otherwise shown on a hotkey, a tray command or `--stdin`; resident with a tray/menu-bar icon offering 显示窗口/立即翻译/退出, `Ctrl+Alt+T` via `global-hotkey`, capture via Ctrl+C/Cmd+C with `enigo` + clipboard with `arboard` (the previous clipboard text is restored after capture); on macOS it reports an Accessibility-permission hint when the clipboard did not change). Esc/X hide the window when a tray or hotkey can restore it, otherwise they quit. The UI is a frameless rounded card (custom draggable header, system light/dark theme) driven by `ModelState` + `TranslationState`: on Windows the window is opaque and DWM-rounded (`with_transparent(false)` plus `DWMWA_WINDOW_CORNER_PREFERENCE`, because wgpu/DX12 on Win32 HWNDs composites transparent pixels black and the card therefore fills the window), while macOS keeps the transparent floating card with margin and shadow; the popup opens near the cursor on the cursor's monitor (Windows: `GetCursorPos` plus a work-area clamp); the translation streams in token by token (skeleton bars before the first token, then a pulsing caret at the end of the text); the window height adapts to the translation (capped at 70% of the monitor, then scrolls) and slides up near the bottom edge so it stays inside the monitor work area; selections captured before the model is ready are queued and translated automatically on ready, failures show an error card with 重新翻译, 复制译文 shows 已复制 for 1.5 s, Ctrl+Enter re-translates and Ctrl+Shift+C copies; on Windows a 替换原文 button (shown when the source window is known) writes the translation back into the source app (`SetForegroundWindow` + Ctrl+V with the previous clipboard text restored). A painted ⇄ button swaps the language pair (the previous translation becomes the new source) and Ctrl+1/2/3 switch to the recent targets, persisted as `recent_targets`; system fonts fall back per script (Chinese/Korean/Japanese/Thai). It **embeds** `translator-service::engine::llama_cpp` (no Ollama, no external service): the model comes from `TRANSLATOR_MODEL_PATH`, config `model_path`, or the per-user default models dir (`translator-core::paths::default_model_path`); if missing and `auto_download` is enabled it is fetched from ModelScope (`translator-core::models`); `check_updates` (default true) shows a window banner and enables a tray item when a newer release exists; on Windows 立即更新 downloads `OpenTranslator-windows-x64.zip` to `%TEMP%\open-translator-update`, extracts it with `Expand-Archive` and runs its `install.ps1`, which stops this process, replaces the binary and restarts the new version in the tray (the banner shows download progress and 重试 on failure), while macOS/Linux open the release page; while running it serves the HTTP API on `service_url` for the browser extension (`serve_extension = false` disables; embedded server code in `src/server.rs`). The hotkey comes from the config file (`hotkey = ...`) or `TRANSLATOR_HOTKEY` (parser in `src/hotkey.rs`, unit-tested on all platforms). Windows/macOS-only deps live under `[target.'cfg(any(target_os = "windows", target_os = "macos"))'.dependencies]`; on Linux the crate builds with stub capture/hotkey/tray, but it now also compiles llama.cpp (cmake + clang needed), so cross-target checks (`--target ...`) no longer work locally — CI builds it on windows and macos runners. `desktop/install-windows.ps1` builds the client into a short `%LOCALAPPDATA%\OpenTranslator\build` target dir (MSBuild FileTracker hits a path-length limit when `llama-cpp-sys-2` builds under a deep repo path) and installs a Startup `--autostart` shortcut to that binary (`-Uninstall` removes it, `-NoStart` skips the tray restart after install); it stops a running instance before building because Windows locks running executables against overwrite; `desktop/install-macos.sh` builds a `~/Applications/OpenTranslator.app` bundle plus a LaunchAgent (`--uninstall` removes both); both warn when no model file is present.
- `browser/extension` holds shared extension sources (plain JS, no bundler): Firefox uses `manifest.json` (MV2, `data_collection_permissions.required = ["none"]`, `strict_min_version` 142), Chrome uses `manifest.chrome.json` (MV3, service worker, `host_permissions`); `browser/build.sh [firefox|chrome|all] [--zip]` copies them into loadable dirs/zips under `browser/dist/` (gitignored) and `browser/sign.sh` signs the Firefox build via `npx web-ext sign --channel unlisted` (needs `WEB_EXT_API_KEY`/`WEB_EXT_API_SECRET`; the xpi download is the last step — do not interrupt; AMO rejects reused version numbers, so bump the manifest version before re-signing). The content script shows a bubble with a target-language selector and an optional auto-translate mode (`autoTranslate`, default off). Validate with `python3 -m json.tool *.json`, `node --check *.js` and `npx web-ext lint --source-dir browser/dist/firefox`; load via `about:debugging` (Firefox) or `chrome://extensions` (Chrome). Note: match patterns cannot contain ports, so the host permission is `http://127.0.0.1/*`. Headless smoke test without a GUI: `browser/test.sh` launches Chrome/Edge with `--headless=new --remote-debugging-port`, loads the MV3 build via CDP `Extensions.loadUnpacked` and drives the service worker plus the content-script isolated world (`--load-extension` is ignored by Chrome 137+; a mock service is started when none is running — building it on a dev machine needs cmake/clang, and the browser log is printed when the debug port does not open).
- `Cargo.lock` is committed per crate; keep them and run `cargo test --locked` when touching dependencies.
- CI lives in `.github/workflows/ci.yml`: `cargo test` for both crates (the desktop job installs `libgtk-4-dev` + `pkg-config`; a `windows-latest` job runs the core tests to keep the service portable), browser static checks + `web-ext lint`, and a Chrome e2e job running `browser/test.sh` (starts a mock-engine service if none is running). Core and Windows/macOS desktop jobs now build llama.cpp (cmake/clang are on the runners; cached after the first run). Releases: `.github/workflows/release.yml` (tag `v*` or manual `workflow_dispatch`) builds the Windows zip (`packaging/windows/install.ps1` + README + exe; the installer stops a running instance before replacing it), the macOS dmg (`packaging/macos/make-dmg.sh` + `Info.plist`, bundle includes the client only) and the Linux deb (`packaging/linux/make-deb.sh`, GTK popup + in-process service) and attaches them to the GitHub release; build steps inject `OPEN_TRANSLATOR_VERSION` from the tag for the update check; use `workflow_dispatch` + `gh run download` to test packaging without tagging. License: MIT (`LICENSE`).
- A root `tests/` dir exists but is not a Cargo test dir — Rust tests belong under `core/translator-service/tests/` or as `#[cfg(test)]` modules. `models/` holds the HY-MT → Ollama import script (`import-hymt-ollama.sh`).
- Root `.gitignore` ignores Rust `target/`, `browser/dist/` and `packaging/linux/build/`; `.kilo/.gitignore` covers JS tooling files inside `.kilo/` only.
- Active branch is `main`.
- Dev-machine runtime (not repo state): Ollama v0.35.0 at `~/.local/opt/ollama` (models in `~/.ollama/models`; installed: `hy-mt1.5-1.8B` GGUFs in `/tmp/kilo/hymt` are ephemeral, `translategemma:4b`, `qwen2.5:7b`, `qwen2.5:3b`; start with `~/.local/opt/ollama/bin/ollama serve`). To build `llama-cpp-2` locally: cmake at `~/.local/opt/cmake` (user-space) and `clang`/`libclang-dev` from apt, with `PATH="$HOME/.local/opt/cmake/bin:$PATH" LIBCLANG_PATH=/usr/lib/llvm-21/lib`. Network quirk: `ollama.com` and HuggingFace are unreachable; ModelScope works and GitHub release assets need a proxy such as `https://gh-proxy.com/`.
- No CI workflows and no rustfmt/clippy config; verify locally with `cargo test`. Existing sources are not rustfmt-formatted, so don't run repo-wide `cargo fmt` unprompted.

## Architecture (current state)

`src/lib.rs` exposes `api`, `config`, `domain`, `engine`; `src/main.rs` is bootstrap only (`Config::from_env()` → `engine::build(&config)` → `api::router(...)` → bind).

Flow: `src/api/mod.rs` (router + handlers + DTOs + error mapping) → `src/domain/` (`translation.rs` types/errors, `language.rs` tag normalization, `prompt.rs` prompt styles) → `src/engine/mod.rs` (`TranslationEngine` trait, `EngineKind`, `build` factory) → `src/engine/mock.rs` / `src/engine/ollama.rs` / `src/engine/timeout.rs` (`MockEngine`, `OllamaEngine`, `TimeoutEngine` wrapper).

- `TranslationEngine::translate` is async and dyn-compatible: it returns `TranslationFuture` (`Pin<Box<dyn Future<Output = Result<TranslationResult, TranslationError>> + Send + '_>>`), and the trait has `Send + Sync` supertraits so API state is `EngineRef` (`Arc<dyn TranslationEngine>`). New engines must use this signature — plain `async fn` in the trait would break `dyn` support.
- `TranslationEngine::translate_streaming` reports decoded pieces through a `DeltaCallback` (`Box<dyn FnMut(&str) + Send + 'static>`); the default implementation emits the complete translation as one delta, `LlamaCppEngine` forwards the inference callback. `engine::build` wraps every engine in `TimeoutEngine`; non-streaming expires the whole request, streaming uses an idle timeout that restarts on every delta (both → `TranslationError::Timeout` / 504).
- Errors: engines return `TranslationError::{InvalidRequest, EngineUnavailable, Timeout, Internal}`; `api` implements `IntoResponse` mapping them to 400/502/504/500 with body `{"error":{"kind","message"}}` (`TranslationError::kind()` is shared with the streaming error event). Empty/whitespace `text` is rejected in the handler with 400.
- API: `GET /health` → `{"status":"ok","service":"translator-core","engine":"<kind>","model":"<model>"}`; `POST /translate` body `{"text","source","target"}` → `{"translation":"[Mock Translation] <text>"}`; `POST /translate/stream` returns SSE events `{"type":"delta","delta":...}` … then a terminal `{"type":"done","translation":...,"elapsed_ms":...}` or `{"type":"error","kind","message"}`.
- Logging uses `tracing` (`RUST_LOG`, default `info`); request logs carry source/target/text_chars/elapsed_ms and error kind but never the raw text.
- Startup warmup is on by default (`TRANSLATOR_WARMUP=false` to disable); warmup failure warns and does not block startup.
- `source`/`target` are accepted but unused by `MockEngine`; `OllamaEngine` builds prompts via `domain::prompt::translation_prompt` (styles: `generic`, `translategemma`, `hymt`) and posts to `{TRANSLATOR_MODEL_URL}/api/generate`, mapping HTTP/connection failures to `EngineUnavailable`. Each style sends its recommended sampling options (`hymt`: 0.7/0.6/20/1.05; others: temperature 0).
- Startup config is env-only: `TRANSLATOR_BIND_ADDR`, `TRANSLATOR_ENGINE` (default `mock`; `ollama` requires `TRANSLATOR_MODEL`, `llama-cpp` requires `TRANSLATOR_MODEL_PATH`), `TRANSLATOR_TIMEOUT_MS` (default `30000`, must be > 0), `TRANSLATOR_MODEL_URL` (default `http://127.0.0.1:11434`), `TRANSLATOR_MODEL`, `TRANSLATOR_MODEL_PATH`, `TRANSLATOR_N_CTX` (default `4096`, must be > 0), `TRANSLATOR_PROMPT_STYLE` (default `generic`), `TRANSLATOR_WARMUP` (`true`/`false`, default `true`), `TRANSLATOR_KEEP_ALIVE` (Ollama keep-alive, default `30m`), `TRANSLATOR_MAX_CHARS` (per-request character cap, default `1500`, over-limit → 400); invalid values abort startup with exit 1. `source` may be `auto` (prompts omit the source language; HY-MT's template is already source-agnostic).

## Conventions

- Commits use conventional prefixes: `feat:`, `docs:` (see `git log`).
- `docs/PROJECT_STATUS.md` and `docs/DEVELOPMENT_LOG.md` are kept as living sprint logs; update them when sprint scope/progress changes, and fix stale statements when touching related code.
- `docs/ARCHITECTURE.md` is the design intent (modularity, model independence, local-first); keep the core crate model-agnostic and platform-independent.
- Releases: use the `release` skill (`.kilo/skills/release/SKILL.md`) — pushing a `v*` tag builds the Windows zip + macOS dmg and creates the GitHub release.
